## 第 1 章　大模型训练对网络的极致挑战

> 打印出来，在方案评审前逐条打勾。**任何一条没打勾，不要进入采购流程。**

### 单位与口径

- [ ] 所有性能条款的**单位**已明确写明 Gb/s 或 GB/s，无一遗漏
- [ ] 所有吞吐指标的**测试口径**已写明（单流 / 多客户端聚合 / 客户端数 / 文件数）
- [ ] 全项目文档中 `Gb/s` 与 `GB/s` 使用一致，无混用
- [ ] 单卡带宽 × 卡数 与 条款要求值做过一次量级核对（防止超物理上限的指标）

### 并行策略与网络需求匹配

- [ ] 明确本集群要跑的并行策略组合（DP / TP / PP / EP）
- [ ] 若含 **EP（MoE）**：收敛比是否按 1:1 设计？（这是硬约束）
- [ ] TP 的通信边界是否限制在单节点 NVLink 域内
- [ ] DP 的梯度同步数据量已估算，并据此推导出所需带宽

### 规模与拓扑

- [ ] 终态规模已确定，且**按终态一次规划**端口分段
- [ ] 已算出两层 CLOS 的规模上限（= 端口数² ÷ 2，本案例 **8192 端点 / 1024 台 / 8192 卡**），并确认终态未越界
- [ ] 已确认「每对 Leaf-Spine 链路数 r」的取值（本案例取 4），并验证 L × r ≤ 128
- [ ] 若越界，三层的方案与成本增量已出
- [ ] 扩容路径确认为"纯加法"：新增设备不改现网路由、轨映射、通信库配置
- [ ] 扩容所需的机柜、供电、配线空间已预留

### 验收条款

- [ ] 规模点不少于 5 个（覆盖小中大）
- [ ] 消息范围覆盖延迟主导区（≤ 32 KB）与带宽主导区（≥ 1 GiB）
- [ ] 正确性判据（`#wrong = 0`）已写入
- [ ] AllToAll 已纳入必测原语
- [ ] 单端口吞吐为**逐口核验**，非抽样
- [ ] 稳定性测试含"失败即从零重新计时"条款
- [ ] 原始日志留存期限已约定（建议 ≥ 180 日）

## 第 2 章　智算中心「五平面」网络架构设计哲学

### 平面划分

- [ ] 每个平面已明确：**流量特征**（带宽 / 突发性 / 延迟 / 丢包容忍）
- [ ] 每个平面已明确：**失效影响等级**与告警级别
- [ ] 每个平面已明确：**管理责任团队**与访问边界
- [ ] 两个平面的告警**需要同时响应**吗？需要 → 必须物理隔离
- [ ] 计算网与存储网已确认隔离方式（本案例：物理隔离，无任何物理连接）

### 网段与地址

- [ ] 每个平面有独立网段，两两做过分组重叠检测（含子网包含关系）
- [ ] 网关地址有专属位置（带内 .254 / 计算网 .1），不与分配地址冲突
- [ ] 地址分配有可心算的规律（本案例：偏移 +10 + 序号）
- [ ] 整机备件有统一保留地址（本案例 .200）
- [ ] 预留段已按用途细分登记，未分配部分写明"未分配"
- [ ] 扩容方式确认不改变现网地址（本案例：/24 → /23，网关不变）

### 容量配比

- [ ] 计算网 : 存储网 的配比按**峰值并发**算，不是按端口数算
- [ ] 已引入"并发系数"修正（算力网非全时满跑，存储网 Checkpoint 期间满跑）
- [ ] 存储交换机端口占用 ≤ 50%（为后续扩容留 4 倍余量）
- [ ] 带外接入数 = 服务器数 + **网络设备数** + 运维设备数（设备数最易漏算）
- [ ] 带外接入余量 ≥ 20%（低于 15% 建议增补交换机）

### 时间同步

- [ ] 是否需要在排障中做跨设备时间对齐？需要 → 必须规划 PTP
- [ ] PTP 是否要求交换机**硬件时间戳**（软件打戳精度不够）
- [ ] 若不立即采购，是否已在预留段登记位置

## 第 3 章　算力网络拓扑设计实战

### 端口配比算术

- [ ] 已按六步法完整算过一遍，含 **Step 3'（轨约束）**
- [ ] 已确认 Leaf 台数是"轨约束"的还是"端点数"的（本案例：24 vs 20）
- [ ] 已算出两层 CLOS 的规模上限，并确认终态未越界
- [ ] 已确认 r（每对 Leaf-Spine 链路数）取值及其冗余含义
- [ ] 每 Spine 端口占用 ≤ 75% 已作为硬约束校核
- [ ] 收敛比按"每 Leaf 上联口 : 下联实用口"计算，未与全网总量混用

### 拓扑与轨

- [ ] 轨归属由卡号唯一确定，与机柜位置无关
- [ ] 同轨 Leaf 只接本轨网卡，无跨轨混接
- [ ] 轨间无直连，全部经 Spine 转发
- [ ] 同轨内跨 Leaf 的跳数已明确（本案例为 2 跳），并已与甲方书面确认
- [ ] 合同中"单跳""零转发"类口语表述已替换为可验证判据

### 分段与扩容

- [ ] 端口按**终态**一次分段（本案例：P1–P64 下联 / P65–P128 上联）
- [ ] 各期只"启用"新端口，不移动已用端口
- [ ] 已识别出唯一的"重排"动作（本案例：二期→三期上联重排）
- [ ] 重排所需的施工窗口已争取并书面确认
- [ ] Spine 补购时序已列入前置条件（本案例：SP09–SP16 须先到位）
- [ ] 四期/越界规模已写进规划文件，作为三层触发线

### 设备选型

- [ ] 交换机端口数已按"终态规模 + 余量"选择，不是按当期规模
- [ ] 已核实所选端口数能撑到终态（本案例 128 口 → 256 台）
- [ ] 施工备用端口已预留（建议 ≥ 25%）
- [ ] 交换机整机冷备件已计入 BOM

## 第 4 章　光模块与光纤物理层深度剖析

### 采购前

- [ ] 已确认**两端设备的端口封装**（不能按链路速率猜）
- [ ] 已确认机房的**最远链路距离**，据此选定 SR / DR / FR
- [ ] 已确认线缆**长度分档**，每档 +5% 备件（禁止按最长距离统一下单）
- [ ] 已确认机房内**只有一种端面标准**（APC 或 UPC 不混用）
- [ ] 已确认 MPO 跳线**只有一种极性型号**
- [ ] 光模块按"链路逐条推导"核算数量，标明服务器侧 / 交换机侧归属
- [ ] 服务器侧模块已在服务器采购合同中明确

### 到货验收

- [ ] 模块型号、封装、波长逐一核对（抽检 ≥ 10%）
- [ ] 同一批次的模块**批次号记录在案**（批次一致性影响后期排障）
- [ ] 线缆长度实测抽检（误差 ±1 m 内）
- [ ] 端面到货即抽检（运输过程也可能污染）

### 施工阶段

- [ ] 施工队配备：一键清洁笔、无尘布、IPA、端面检测仪、光功率计
- [ ] 已做**施工交底**：清洁 SOP、极性唯一型号、禁止混插
- [ ] 每次插拔前必清洁
- [ ] **逐芯端面检测并拍照归档**
- [ ] 光功率实测，**裕量 ≥ 3 dB 才算合格**
- [ ] 插损记录归档（每链路一条）
- [ ] 弯曲半径符合 OM4 要求（通常 ≥ 20 mm）

### 验收

- [ ] 全部链路有 OTDR 或插损测试记录
- [ ] 全部链路有端面检测记录
- [ ] 光功率裕量不达标的链路已整改并复测
- [ ] 备件模块与线缆已入库登记

## 第 5 章　服务器、网卡与芯片级互联

### 服务器与网卡配置

- [ ] 每节点网卡数量与 GPU 数量符合配比设计（本案例 1:1，8 卡 8 网卡）
- [ ] 网卡封装与服务器端口一致（本案例 OSFP）
- [ ] 已按 5.2.2 的算术核算：**单卡承载带宽 ≤ PCIe 单方向可用宽度**
- [ ] 已知本平台的 PCIe 代数与 x16 单方向带宽（本案例 PCIe 5.0 = 63 GB/s）

### PCIe 链路核验

- [ ] 逐卡检查 `lspci -vv` 的 `LnkSta`，与 `LnkCap` 一致
- [ ] 无 x16 掉到 x8 / 32GT/s 掉到 16GT/s 的情况
- [ ] 主板 bifuration 配置已确认，不会把 x16 拆错

### GPU–NIC 亲和性（**最高优先级**）

- [ ] 逐台执行 `nvidia-smi topo -m`
- [ ] 统计每条 GPU-NIC 对的拓扑等级（PIX / PXB / PHB / NODE / SYS）
- [ ] **SYS 数量符合设计预期**（本案例要求 0）
- [ ] 发现 SYS 的服务器已调整网卡插槽并复测
- [ ] 亲和性检查结果已归档

### 芯片级互联边界

- [ ] 已确认 NVLink 域大小（本案例 8 卡）
- [ ] 已确认 GPU 是 SXM 还是 PCIe 形态（决定域内带宽量级）
- [ ] **TP 规模已锁定在 NVLink 域内**（本案例 TP ≤ 8）
- [ ] 已按 5.2.5 的表核对：网络只承载"出网口"的流量
- [ ] 若未来可能扩大 TP，已评估网络压力模型的变化

### 验收手段

- [ ] **单端口压测逐口执行**，不抽样（本案例 ≥ 360 Gb/s / 口）
- [ ] 压测结果与服务器-端口映射表一一对应归档
- [ ] 逐台核验 SN、GPU UUID、NIC GUID、磁盘 SN
- [ ] GPU 诊断执行 DCGM（本案例 Level 3 全量 + Level 4 抽取）

## 第 6 章　InfiniBand（IB）无损网络全景

### 方案评估阶段

- [ ] 已列出供应商唯一性风险，并评估可接受程度
- [ ] 已确认目标型号的**备件供应年限**条款（建议 ≥ 5 年）
- [ ] 已确认管理软件（UFM 等）的**授权方式与费用**（按端口？按台？）
- [ ] 已确认固件升级策略（能否自主决定升级窗口）
- [ ] 已评估出口管制 / 国产化合规要求对选型的影响
- [ ] 已确认备件渠道与交期承诺（写入合同）

### 部署阶段（若选 IB）

- [ ] SM 部署为**双机主备**，优先级不同
- [ ] SM 管理路径独立于业务路径
- [ ] SM 主机本身高可用
- [ ] 已配置 **SM 拓扑新鲜度监控**（不只是进程存活）
- [ ] 已配置 SM 故障告警
- [ ] LID 分配方案与 IP 规划一样形成文档（不要只存在于 SM 里）

### 运维阶段

- [ ] 有定期核对"拓扑与实际链路"的一致性流程
- [ ] 扩容后主动触发拓扑重发现并核对
- [ ] 备件按"单点故障影响"分级配置，不是简单按百分比
- [ ] 整机冷备件至少 1 台（不论规模）
- [ ] 固件与 SM 版本升级有配套验证流程

## 第 7 章　超大规模无损以太网（RoCEv2）组网实战

### 设计阶段

- [ ] 已确认无损流量的**数量**（本案例通过物理隔离降到最少）
- [ ] 已从规格书确认：每端口可用缓冲深度
- [ ] 已完成 **headroom 计算**（400G 约 160 KB 量级）
- [ ] 已规划 **DSCP → 802.1p → TC → 无损队列** 的完整映射链
- [ ] 已确认 DSCP 取值，并约定全网统一
- [ ] 已确认交换机支持 **PFC Watchdog**
- [ ] 已确认交换机支持基于队列长度的 **ECN 概率标记**

### 配置阶段

- [ ] 算力无损队列已配置并绑定到正确 TC
- [ ] **每一台**交换机都配了（不是只配模板里的）
- [ ] XOFF 阈值 ≤ 端口缓冲 − headroom
- [ ] ECN 的 Kmin < Kmax < XOFF，形成三级台阶
- [ ] DCQCN 参数（速率恢复曲线等）已配置
- [ ] PFC Watchdog 已开启，阈值已设置
- [ ] 服务器网卡侧 DSCP 打标与交换机信任模式一致
- [ ] 全设备配置导出，与基线比对无差异

### 验证阶段

- [ ] 单流带宽测试通过（本案例 ≥ 360 Gb/s / 口）
- [ ] **多对多并发压测（主动造拥塞）** 已执行
- [ ] 造拥塞期间：ECN 计数上升、PFC 计数小幅、`#wrong = 0`、吞吐稳定
- [ ] 记录稳态下的 PFC / ECN 计数基线（作为后续运维的参照）
- [ ] 无损参数配置与调优过程已文档化归档

### 运维阶段

- [ ] PFC / ECN 计数已纳入监控与告警
- [ ] PFC Watchdog 触发有告警
- [ ] 有配置基线与定期比对机制
- [ ] 扩容后有参数回归验证流程

## 第 10 章　高性能智算存储网络

> 本章清单聚焦"存储是否会成为训练阻塞点"。可直接打印带到机房。

**A. 需求与容量规划（设计阶段）**

- [ ] 客户需求是否区分了**裸容量**与**可用容量**（EC 后）？1 PB 是裸还是可用，必须书面锁定
- [ ] 是否按"**盘数决定吞吐、单盘容量决定容量**"两条线分别核算，而不是用总容量反推
- [ ] 冷存盘型是否**明确写为 CMR**，并在采购清单里写到具体型号
- [ ] 是否做过"大盘 / 中盘 / 小盘"三方案吞吐对比（10.2.2 的算式）
- [ ] 并行文件存储的 **OST / MDS 配比**是否按数据集的小文件/大文件特征定过

**B. 网络接入（拓扑阶段）**

- [ ] 存储流量是**融合组网**还是**独立平面**？若融合，是否算过单节点上限（挂 Leaf 12.5 Gb/s vs 挂 Spine 100 Gb/s）
